## 1. 系統全景架構圖
* 構建一個能夠處理 1 到 6 路高畫質 IP 攝影機（包括 Axis 或任何支援 RTSP 的品牌），且具備網頁/視窗關閉不中斷錄影、自動斷線重連、零 CPU 壓縮損耗的工業級系統，最頂級的架構就是 「後端多行程精靈（Multi-processing Daemons） + 核心共享記憶體（Shared Memory） + PyQt6 前端監控台」。


* 在作業系統（OS）層級中，我們的系統會被拆分為多個完全隔離的行程（Process）。即使前端 UI 崩潰或被點擊「叉叉」關閉，後端的錄影行程依然會安穩地在 RAM 與硬碟之間運作。

* 架構圖：
========================================================================
 🟢 1. 實體 IP 攝影機層 (Physical IP Camera Layer)
========================================================================
     ┌──────────────────────┐          ┌──────────────────────┐
     │ Axis Camera (Cam 1)  │          │ Other Camera (Cam 2) │

                 ▼                                 ▼
========================================================================
 ⚙️ 2. 後端多行程精靈層 (Backend Daemon Process Layer)
      👉 獨立運作 / 24小時不斷線 / 支援 1 至 6 路獨立行程
========================================================================
     ┌──────────────────────┐          ┌──────────────────────┐
     │ recorder_daemon.py   │          │ recorder_daemon.py   │
     │      (Cam 1)         │          │      (Cam 2)         │

 🧠 3. 作業系統 RAM 層 (OS Shared Memory Layer)

========================================================================
                     ┌───────────────────────────┐
                     │        pyqt_gui.py        │
                     │    (2x3 多路網格監控台)    │
                     └───────────────────────────┘
 

* 這個架構的核心優勢：
* **零拷貝（Zero-copy）：後端 OpenCV 抓到的 Raw 影格矩陣直接寫入 RAM 共享記憶體區塊。前端 PyQt 直接映射（Map）該記憶體位址來渲染，不需要透過網路協議傳輸，也不需要壓縮成 JPEG，CPU 消耗降到極致。
* **完全解耦（Decoupling）：UI 的生死（開啟/關閉/當機）與錄影核心完全無關。
* **動態故障轉移：如果第 2 路攝影機斷線，第 2 路後端行程會自己進入重連迴圈，並在共享記憶體上畫「斷線警告」，第 1, 3, 4, 5, 6 路完全不受影響。

## 6. 錯誤日誌記錄需求

在處理錯誤或撰寫擷取異常（Exception）的代碼時，必須實作符合以下嚴格規則的錯誤日誌記錄機制：
- **日誌路徑與命名**：日誌必須存放在 `include/_config.php` 定義的 `$_log_folder_path` 目錄下。檔名必須為當天日期 `YYYY-MM-DD.log`（若不存在則系統自動建立）。
- **目標檔案**：所有執行階段錯誤（Runtime errors）必須記錄至名為 `error-YYYY-MM-DD.log` 的檔案中。
- **動態日期**：`YYYY-MM-DD` 必須替換為錯誤發生時的當前系統日期。
- **檔案管理**：寫入前必須先檢查當日的日誌檔案是否存在。若檔案不存在，必須自動建立該檔案。
- **寫入方式**：一律以「附加（Append）」方式將新錯誤寫入檔案，絕對不能覆蓋現有的日誌內容。
- **日誌格式**：每條紀錄必須包含詳細時間戳記（HH:mm:ss）、錯誤訊息（Error message），以及追蹤堆疊（Stack trace，若可用）。

## 7. 防禦性程式碼與日誌常規 (Logging & Exception Handling)
*   **日誌路徑與命名**：日誌必須存放在 `include/_config.php` 定義的 `$_log_folder_path` 目錄下。檔名必須為當天日期 `YYYY-MM-DD.log`（若不存在則系統自動建立）。
*   **日誌內容規範**：
    *   程式啟動時，必須寫入 `[START TIME] YYYY-MM-DD HH:mm:ss - 同步程序啟動`。
    *   每個核心步驟（如：讀取 Sheet、檢查專案主檔、更新資料庫、回寫 Sheet）皆必須加入 `DEBUG` 層級的日誌輸出。
    *   程式結束時，必須寫入 `[END TIME] YYYY-MM-DD HH:mm:ss - 同步程序順利結束`。
*   **異常處理 (Try-Catch)**：
    *   所有 API 呼叫與資料庫查詢必須使用 `try/catch` 包覆。
    *   發生錯誤時，必須同時在命令列終端機顯示錯誤訊息，並將詳細錯誤軌跡 (Stack Trace) 寫入 `YYYY-MM-DD.log` 日誌中，確保程式不會無預警中斷崩潰。
